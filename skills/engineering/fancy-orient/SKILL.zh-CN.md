# Fancy Orient

建仓之前的产品真相。**永远不要 `git init`。** 永远不要一上来就考三问。永远不要一上来问「你觉得什么工具烦」。

本对话里已经说过要做什么，那就是种子 — 去调研那个领域。不要再问一遍。

还不知道，就只问 **一句**：**你想做什么？** 一个名字、一个品类、或「还没想法」就够。然后调研。在他们说出想做什么之前，不要采访痛点、用户、或讨厌哪些应用。

不要假装有 `/product-lens`、`/grill-me`、`/exa-search`、`/to-prd`。检索和拷问都在本技能里做。

## 顺序（不许打乱）

1. **意图** — 还不知道就问一句：你想做什么？已经知道就跳过。
2. **调研（第 1 步）** — 除非命中下面的跳过规则。在**那个领域**产出证据。亮出来。等用户反应。
3. **三问（进入第 2 步的门）** — 他们看过证据之后再问。每问都锚在证据上，让他们挑选和纠正，而不是对着空白编。
4. **拷问** — MVP vs 不做清单，谁**不是**用户。
5. **`proposal.md`** — 写文件。复述 Pitch / MVP / 不做清单。**停。** 问对不对。改到他们接受。这才算握手完成。

## 几乎不要跳过调研

跳过第 1 步 **仅当** 用户已经在本对话里用**自己的话**答稳三问、没有含糊（或他们贴来一份完整的 `proposal.md`）。

**不要**因为起了个名字、或说「我知道要做什么」就跳过。名字 ≠ 痛点。三问里任何一问还是猜的，就先调研。

## 调研（第 1 步）

不要搜「什么点子好」。搜「什么东西烂」。引用真实抱怨（**这次打猎返回的 URL** + 一句）。禁止编造帖子。

**不要用 Claude Code 的 `WebSearch` 或 `WebFetch`。** 那是 Anthropic 服务端工具。走代理（`ANTHROPIC_BASE_URL` 不是 api.anthropic.com）时只会得到 `Did 0 searches` 和 `API Error: Content block not found`。改成本地打猎：

```bash
python3 <本技能>/scripts/hunt.py "检索句一" "检索句二"
```

脚本就在这份 `SKILL.md` 旁边（安装后：`.claude/skills/fancy-orient/scripts/hunt.py`）。跑 **2–3 条查询** 就停。报错或 0 行，告诉用户。**不要**再试 `WebSearch`。**不要**用「领域知识」填痛点表。

**日期：** 搜之前先知道今天（harness 的「Today's date」，或跑 `date`）。禁止猜年份。查询里不要写 `2024` 或任何过期年份。需要「最近」就用今年和去年，或者干脆不写年份。

| 他们有什么 | 你做什么 |
| --- | --- |
| **有种子**（他们已经说了想做什么：名字或品类） | 打**那个领域**。现有产品的一星、「我讨厌…」、「为什么没有一个工具能同时做 A 和 B」。不要逛到无关领域。 |
| **没想法**（他们明确说还没有） | 选一条猎人路径：**痛**（真实抱怨）、**缝**（一星差评 / 拖了多年的 Feature Request）、或 **沿**（新模型/API + 旧工作）。去搜。在亮出证据之前，不要替他们发明一个产品。 |

然后在草稿环境里展示（对话，或他们指定的笔记路径 — 仍然不建仓）：

- **痛点清单**（5–10 条，带引用）
- **3–5 个竞品**以及它们败在哪
- **一句话方向**（更薄 / 更垂直 / 更老实的工具会长什么样）

可选：用这些引用，扮演目标用户做 2–3 轮短角色扮演，让他们感到痛。

问：「这些里哪条是*你的*痛？我哪里搞错了？」然后 — 也只有这时 — 才问三问。

方向被打回，就再打一轮。仍然不建仓。

检索句式见 [HUNT.md](HUNT.md)。

## 三问（门槛）

用户来答。你可以从**证据**里提议；他们确认。不稳或缺失 → 继续调研或继续谈。不要开仓库。不要写 `design.md`、`visual.md`、`tasks.md`、`decisions.md` 或数据库 schema。

1. **谁**在用？
2. 有**多痛**？
3. **为什么现在**做？

每一问都从调研里长出分叉（哪条引用、他们从哪个现有产品跳开）。不要甩三个空问题。

三问都稳 → 拷问，然后写 `proposal.md`。这就是握手。

## 拷问（写文件之前）

就 MVP vs 不做、谁不是用户、什么情况下不值得做，问 3–5 个对抗性问题。等回答。这些还糊着时不要写 `proposal.md`。

## 提案

三问稳定之后，写 `proposal.md`：

- **还没有 git 仓库：** 当前目录，或用户指定的路径（Obsidian 可以）。不清楚就问。
- **已经是仓库：** `specs/core/proposal.md`（若他们点名功能则 `specs/<feature>/proposal.md`）。

章节见 [PROPOSAL.md](PROPOSAL.md)。填 Pitch、Problem、Tension、Goals（谁 + 一个 MVP）、Non-Goals、Vibe、Assumptions。三问用用户的原话。User Flows 和 Acceptance Criteria 可以先留草稿。**不要 schema，不要拆任务。**

文件在他们接受之前都是草稿。写完后在对话里复述 **Pitch、那一个 MVP、不做清单**。问：这份对吗？要改哪段？他们说提案对了（或指出修改、你改完再问一遍）之前，不要告诉 `/fancy-flow` 握手完成，也不要开始 `/fancy-shape`。

接受过的提案也可以收回。他们后来说不对，就变回草稿。改，等接受，再问 `/fancy-flow` 后面哪些产物要重做。除非他们也要换品类，否则不要重新打猎。

## 完成标准

- [ ] 三问之前已经做过调研（或命中跳过规则）
- [ ] 用户能不打结巴地说出谁用 / 多痛 / 为什么现在
- [ ] MVP 是一个能力，不是清单
- [ ] Non-Goals 写明了
- [ ] 磁盘上有 `proposal.md`，**且用户接受了**
- [ ] 本技能里没有发生 `git init`

告诉 `/fancy-flow`（或用户）握手完成。停。不要初始化项目 — 那是 `/fancy-shape`。不要在同一轮里调用 shape。
