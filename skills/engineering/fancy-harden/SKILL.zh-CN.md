# Fancy Harden

测试和真相对齐是同一条环：抓住谎言（mock 演戏、路径缺失），修好，锁回归。口头不算证据。

## 进门

最好在 `/fancy-build` 之后。小工具可以少上自动化，但主路径必须带着日志或截图走过。

## 铁律

1. 模型说通过不算通过。要命令日志、网络记录或截图。
2. 写了功能的那个 Agent 不该是核心路径的唯一判官。用户能新开会话时，破坏性用例和 e2e 优先换新会话。
3. 每个 bug 变成测试，或写进 `memory/FAILURES.md`。
4. 后端关掉 UI 还能显示数据，就是演戏。修掉或写成任务；不要带着它发布。
5. 证据大于解释。没有日志 → 当作没跑过。

## 测试（第 8 步）

按序 — 不要从单元测试开场：

1. **真实性审计** — 搜 mock / fakeData / 写死的夹具 / 假装网络的 `setTimeout`。列出路径、用途、保留还是替换。有后端就出示一次真实请求日志。
2. 静态：lint / 类型，带命令输出。
3. 单元：核心逻辑。敌对用例（空、溢出、坏输入）最好另开一轮。
4. E2E / 主路径：把 shape 的测试契约对准真应用来跑。真实命令、真实输出，贴出或存下。
5. 用户自己用一次。记下任何「感觉不对」。**停**，直到他们用过（或明确跳过）。不要在同一轮里让 `/fancy-flow` 去发布。

shape 的测试契约就是考卷。不要另写一套只会附和刚写代码的测试。

## 漂移（第 8.5 步）

验收和意图对不上时，不要内省。任何修改之前先做物理诊断：

1. 读该特性在 `proposal.md` 和 `design.md`（以及原型）里的原文 — 把句子引出来。
2. 把实现和那段文字做 diff。
3. 跑相关测试；读日志。

给漂移起名：

| 种类 | 含义 | 修法 |
| --- | --- | --- |
| 实现漂移 | 规格对，代码错 | 先写失败测试，再改代码 |
| 理解漂移 | 代码符合对用户的错误理解 | 先和用户对齐，再改代码 |
| 定义漂移 | 规格太糊 | 同时改规格、任务和代码。新规则先写失败测试 |

一次过把四处对齐：规格、代码、测试，以及若存在则含 `memory/ARCHITECTURE.md` / README。

Mini+：把防漂移铁律追加进 `CLAUDE.md`（先物理诊断再推测；禁止口头「已修复」；测试即真相）。Micro 仓库不要发明 Husky/CI；Pro 若还没有提交前测试钩子，可以加一个。

## 完成标准

有验证日志（命令 + 输出），mock 演戏已消失或被明确豁免，未关的漂移已修或已写成任务，Mini+ 的 `CLAUDE.md` 有防漂移句，**且用户自己用过一次**。告诉 `/fancy-flow`。不要在同一轮里开始 `/fancy-ship`。
